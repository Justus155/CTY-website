## Security deployment

This is a static Supabase client. The `sb_publishable_` key and project URL are public identifiers, not secrets. Never put a service-role/secret key, SMTP password, or CAPTCHA secret in browser code or a published `.env` file. Rotate any actual secret that has ever been committed. There is no package manifest or local server in this repository; Supabase JS loads from a CDN. Review and pin the CDN version as part of a tested dependency update.

1. Run [SQL QUERIES/postPolicies.sql](SQL%20QUERIES/postPolicies.sql) in the Supabase SQL Editor before deploying these pages. It requires existing `profiles`, `posts`, `events`, `event_rsvps`, and `leaders` tables and the `media` and `leaders` buckets. Back up data first; remove duplicate `(event_id, user_id)` RSVP rows before creating the unique index. Review **all** existing policies on these tables and buckets: PostgreSQL ORs permissive policies, so an old broad policy can still grant access. Audit `profiles` own-row read/write policies and bucket MIME/type and size limits too. These SQL changes do not take effect until applied to the project.
2. Assign admin rights only from a trusted server/service role. The removed admin setup page must not be hosted. The profile guard rejects browser changes to `role` and `is_admin`; test that a normal account cannot update either field, insert posts/leaders/events, or read another member's RSVP. Test that an admin can still manage content. The UI's admin checks are only presentation; RLS is the authorization boundary. Review any other Edge Functions and their JWT verification separately.
3. Supabase Dashboard: enable email verification, leaked-password protection, authentication rate limits, and CAPTCHA on signup/signin/recovery; configure TOTP MFA and require `aal2` for privileged operations once enrollment/recovery flows exist. Configure allowed redirect URLs, API CORS origins, and Edge Function CORS separately. Do not expose the service-role key to the browser. Set storage upload limits and validate uploads server-side.
4. Host: force HTTPS and configure HSTS, `X-Content-Type-Options: nosniff`, `Referrer-Policy: strict-origin-when-cross-origin`, a restrictive `Permissions-Policy`, and a tested Content Security Policy. The site currently uses inline scripts/styles and external Google Fonts and `esm.sh`; a strict CSP needs those scripts/styles moved to files or nonce/hash support. Do not deploy a policy that breaks existing pages. Disable directory listing and block publication of `.git`, `.env`, backups, and SQL files. Set rate limits on the host/Edge Functions for write endpoints; client-side timers are not security controls.

Sessions are tab-scoped in `sessionStorage`, not `localStorage`, and end when the tab closes. Existing sessions in the old storage location are discarded; members will need to sign in again. JavaScript-accessible sessions are still vulnerable to XSS; HttpOnly/Secure/SameSite cookies require a trusted server/BFF and cannot be implemented by this static site. Browser-side Supabase queries use parameterized PostgREST filters, not SQL string concatenation. Form validation in JavaScript is for UX; enforce bounds and ownership in the database and at any server endpoint.

## Post upload limits

Posts accept JPG/PNG/WEBP photos up to 10 MB and MP4/WebM videos up to 150 MB. Files above 6 MB use resumable TUS uploads. In Supabase Storage Settings, set the global file size limit to at least 150 MB; set the `photos` bucket limit to 10 MB and the `videos` bucket limit to 150 MB, with matching allowed MIME types and admin-only upload policies. Supabase Free projects cannot set a global limit above 50 MB, so 150 MB videos require a project plan that supports that limit. Client-side checks alone do not raise or enforce server-side limits.

Video length depends on bitrate, not just resolution: at 5-10 Mbps, 150 MB is roughly 2-4 minutes, including some variation for audio and encoding overhead. Lower bitrate lasts longer; higher bitrate lasts less time.
